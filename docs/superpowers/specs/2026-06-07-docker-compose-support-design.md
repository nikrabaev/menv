# menv — docker-compose support (design)

**Date:** 2026-06-07
**Status:** Design, pending implementation
**Author:** brainstormed with the menv author

## Problem

menv makes the vault the single source of truth for env vars and generates
`.env` files for app consumers on demand. One large source of manual toil
remains: **docker-compose files**. Every time a variable is added to or removed
from a service, someone hand-edits the service's `environment:` block. menv
should automate add/remove of variables to/from compose services the same way it
automates `.env` files — driven by wiring, never by hand.

## Constraints that shape the design

- A `docker-compose.yml` is **hand-authored and committed**. Unlike a generated
  `.env` (a disposable output menv owns wholesale), menv must **not** own the
  whole file — only a delimited *region* inside specific services. Everything
  else (service definitions, volumes, networks, anchors, comments, other env
  entries) is untouchable.
- The unit that consumes env vars is the **service**, not the file. One compose
  file has many services, each wanting a different subset of variables.
- Compose delivers `${VAR}` interpolation from a **single project env file** per
  compose project (`./.env` by default, or one chosen with `--env-file`), **not**
  from `env_file:`. Interpolation is therefore **global to the project**, not
  per-service — which is why same-named variables across services must be
  disambiguated.
- Secrets must never enter the committed YAML (menv's core rule).

## Decisions (resolved during brainstorming)

1. **Mechanism:** `environment:` entries with `${VAR}` interpolation references
   (not `env_file:`, not literal values). Names stay visible and reviewable in
   the YAML; secrets are never committed (only `${...}` references are).
2. **Value source:** menv generates a **`.env.compose`** file in each compose
   project directory for interpolation. Because the name is not compose's default,
   runs pass `--env-file .env.compose` — which keeps the compose interpolation
   file cleanly separate from any app's own `.env`. A deploy platform can still
   override at runtime.
3. **Region delimiting:** marker comments naming an existing consumer:
   `# <menv:NAME>` … `# </menv>`.
4. **Link model:** the marker *is* the link. menv discovers links by scanning
   compose files for markers — **no manifest schema change**, fully derived
   file-state. One consumer may be linked from many services.
5. **Environments:** active-environment single `.env.compose` (single-mode).
   The `${...}` references are env-agnostic; only the generated `.env.compose`
   values are env-specific. `menv generate --env prod` flips the values.
6. **Unapplied vars:** the compose YAML region lists **every** wired variable as a
   live (uncommented) `${...}` reference — the block declares the full wired
   surface regardless of applied state. The applied/unapplied distinction is
   carried by `.env.compose`, where an unapplied value is **commented out**
   (`# KEY=value`), matching menv's `.env` convention. (Consequence: an uncommented
   `${KEY}` whose value is commented in `.env.compose` makes `docker compose`
   interpolate it to an empty string, with a "variable not set" warning — the
   container gets `KEY=` rather than the key being absent.) This makes the YAML
   region fully **env-independent**.
7. **CLI surface (v1):** **markers only** — no new commands. menv fills regions
   during `menv generate` and TUI save. No `src/cli/compose.ts` in v1.
8. **Interpolation key prefixing:** **always** prefix the interpolation key with
   the consumer name (`${CONSUMER_KEY}`). The container variable name (left of
   `=`) stays the real name. Uniform, collision-free by construction, no
   detection logic, no edge cases.

## The model

A compose service opts itself into menv by carrying a marker that names an
**existing consumer** (the same token used with `--scope`, e.g. `api`, `web`,
`root`):

```yaml
services:
  api:
    image: myorg/api:${TAG}        # hand-authored interpolation, untouched
    environment:
      - NODE_ENV=production         # hand-authored, untouched
      # <menv:api>
      - DATABASE_URL=${API_DATABASE_URL}
      - REDIS_URL=${API_REDIS_URL}
      # </menv>
```

For each `# <menv:NAME>` region, menv writes one entry per variable **wired to
consumer `NAME`** (every wired variable, regardless of applied state — the block
declares the full surface). The container variable name is on the left; the
interpolation key is the consumer-prefixed name. The values live only in the
generated, git-ignored `.env.compose`, where a value **unapplied** in the active
environment is commented out:

```dotenv
# ./.env.compose (beside the compose file) — git-ignored, generated by menv
API_DATABASE_URL=postgres://api…
API_REDIS_URL=redis://…
WEB_DATABASE_URL=postgres://web…   # web's distinct value — no collision with api's
```

`wire`/`unwire` a variable to `api`, or toggle applied state, and the region
updates on the next generate. That is the automation.

### Why always-prefix resolves the hard case

Two services (`api`, `web`) can both expose a container var named `DATABASE_URL`
with **different** values — in menv these are two distinct vault variables sharing
a name. A single project `.env` cannot hold two `DATABASE_URL=` lines, and
interpolation is global. Because every interpolation key is consumer-prefixed
(`API_DATABASE_URL`, `WEB_DATABASE_URL`), the keys never collide within the single
shared `.env.compose`, and each container still receives its correct
`DATABASE_URL`. (Keeping `.env.compose` as its own file also means it never mixes
with an app's own `.env`.)

## Marker syntax

- Open: `# <menv:NAME>` where `NAME` is the consumer's addressable token (the
  same resolution used by `--scope` / `wire`). `root` is valid.
- Close: `# </menv>` (bare; regions do not nest — menv matches the nearest close
  after an open).
- Placement: inside a service's `environment:` block. The region's generated
  lines and closing marker adopt the **indentation of the open-marker line**.
- A marker naming an **unknown consumer** is a **non-fatal warning**; menv leaves
  that region untouched and continues.

## Region rendering rules

For consumer `NAME` (the region body is **env-independent**):

- Take **all** base variables wired to `NAME` (reuse `varsForConsumer` from
  `src/core/model.ts`; applied state does not filter the region), sorted by group
  then name, with **ungrouped variables last** — a deterministic, locale-independent
  comparison. (This intentionally differs from `generate.ts`'s `sortedVars`, whose
  `"~"` sentinel + `localeCompare` can sort ungrouped variables *first* on some
  platforms for the `.env` files; unifying the two orderings is a possible
  follow-up and out of scope here.)
- Emit, at the marker's indentation, one entry per variable:
  - **Sequence style** (default): `- KEY=${PREFIX_KEY}`
  - **Mapping style** (if the block is a YAML mapping): `KEY: ${PREFIX_KEY}`
  - Style is detected from the surrounding `environment:` node via a light YAML
    parse; default to sequence when ambiguous/empty.
- `PREFIX` = consumer token uppercased with every non-`[A-Za-z0-9_]` char replaced
  by `_` (e.g. `web` → `WEB_`, `@acme/api` → `ACME_API_`, `root` → `ROOT_`).
- Unapplied variables are **not** omitted — they appear as live references like any
  other; their applied/commented state is reflected only in `.env.compose` (below).
- An empty region (no variables wired to the consumer) leaves the body empty
  between markers.

### Editing approach

menv performs a **line-based splice**: locate the open/close marker lines, replace
only the lines between them, and leave the rest of the file byte-for-byte intact.
This avoids reserializing the whole YAML (which would reflow unrelated services,
comments, and anchors). A light YAML parse is used only to *locate* services /
detect list-vs-map style, not to rewrite the document.

## `.env.compose` generation

- Granularity: **per compose-project directory**, not per file. Multiple compose
  files in one directory (`docker-compose.yml` + `docker-compose.override.yml`)
  share one `.env.compose`, matching how `docker compose` loads stacked files. It
  is the **union** of every region's referenced variables across all compose files
  in that directory.
- Contents: `PREFIX_KEY=value` for each referenced variable in the active
  environment; a value **unapplied** in that environment is emitted commented-out
  (`# PREFIX_KEY=value`), per menv's `.env` convention. Keys are always prefixed,
  so the union is collision-free.
- Path/name: `.env.compose` in the compose project directory — always its own
  file, **never** merged into an app consumer's `.env`. Already git-ignored by
  menv's standard `.gitignore` block (`.env.*` matches recursively;
  `!.env.example` is the only exception).
- Usage: runs pass `docker compose --env-file .env.compose …`. The compose file's
  own `${...}` (image tags, ports) interpolate from it too. Without `--env-file`,
  compose falls back to its default `./.env` and the `${PREFIX_KEY}` references
  would be unset — so this flag is the one usage requirement to document.
- Secrets: real values land in `.env.compose` (git-ignored) exactly as in any
  other generated env file. The committed YAML carries only `${...}` references.

## Discovery

- At scan/generate, glob conventional compose filenames under the repo root —
  `**/{docker-compose,compose}*.{yml,yaml}` — excluding `node_modules`, `.git`,
  `.menv`.
- Parse each, enumerate services, scan for `# <menv:NAME>` regions.
- Links are **derived state** — re-read every time, persisted nowhere. No
  `menv.toml` / manifest change.

## Generation hook

`writeGeneratedFiles(model, env, stamp)` in `src/io/generate.ts` gains a compose
step after app `.env` generation:

1. Discover compose files (glob).
2. Group by directory; for each region, splice the rendered body into the file.
3. Write each directory's `.env.compose` (union, prefixed, active env) — its own
   file, independent of app `.env` generation.

Both `menv generate` (headless/CI) and TUI save go through this path, so compose
regions and project `.env`s stay in sync with the vault automatically.

## Testing plan

- `findRegions`: detects open/close, captures consumer token + indentation;
  ignores non-marker comments; handles missing close (warn/skip).
- `renderRegionBody`: applied-only; prefixing; group/name ordering; sequence vs
  mapping style; empty region; secret values never appear (only `${...}`).
- `spliceRegions`: replaces only between markers; preserves everything outside
  byte-for-byte; preserves indentation; multiple regions in one file; multiple
  consumers.
- `renderComposeEnv`: per-directory union; always-prefixed keys; active-env
  values; collision-free across consumers with same-named distinct variables;
  written as its own `.env.compose`, never merged into an app `.env`.
- `discoverComposeFiles`: matches conventional names; excludes
  `node_modules`/`.git`/`.menv`; groups by directory.
- Unknown-consumer marker → warning, region untouched.
- Integration through `writeGeneratedFiles`: wire/unwire reflects into regions;
  env switch flips project `.env` values; YAML outside regions is stable.

## Edge cases & notes

- Hand-edits **inside** a region are overwritten on the next generate (menv owns
  the region), matching the `.env` contract. Drift-import for regions is a
  deliberate fast-follow (see Out of scope).
- A service whose `environment:` would become only menv comments + no entries can
  parse as `null`; menv warns rather than producing an invalid block.
- `docker-compose.prod.yml`-style files are scanned like any other; v1 does not
  special-case per-env compose files (active-env model). Markers are user-curated.
- Multi-line values remain unsupported (existing menv limitation).

## Alternatives considered (rejected)

- **`env_file:` reference** instead of `environment:` refs — simplest and
  secret-safe, but the variable names would not appear in the YAML, which is the
  reviewability the author wants; and the git-ignored file must exist at runtime.
- **Literal values inline** (`KEY: value`) — would commit secrets in plaintext;
  violates menv's core rule.
- **menv owns the whole `environment:` block** / **key-tracked, no markers** —
  rejected for clobbering hand-authored entries / fragile manifest-only state.
  Markers won: explicit, diff-visible, drift-friendly, and the link travels with
  the file.
- **Per-service / disambiguate-on-conflict prefixing** — prettier common case but
  introduces mixed styles, churn, and co-located-`.env` edge cases.
  Always-prefix chosen for a uniform, collision-free, zero-edge-case rule.
- **Per-env project files** (`--env-file`) — deferred; active-env single file is
  simpler and matches menv's default consumer mode.

## Out of scope (fast-follow)

- Region **drift-import** at TUI launch (hand-added `- FOO=${FOO}` ⇒ wire FOO;
  commented/removed ⇒ unapplied), reusing `src/io/drift.ts` machinery.
- TUI inspector display of a consumer's **linked services**.
- `menv compose list | link | unlink` convenience commands.
- Per-env compose files (e.g. `.env.compose.<env>` selected per environment).
